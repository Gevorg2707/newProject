## 1. Positioning և առաջին վճարող հաճախորդը

**Positioning (մեկ նախադասություն).** «Առևտրաչափ»-ը Հայաստանի փոքր ու միջին մանրածախ բիզնեսի սեփականատիրոջը շաբաթական մեկ տեղում ցույց է տալիս, որ ապրանքն իրականում շահույթ է բերում, որը՝ ոչ, և որ 2–3 որոշումն արժե փորձարկել հաջորդ շաբաթ՝ իր իսկ ՀԾ-ի, գովազդի և բանկի արտահանած ֆայլերից, առանց որևէ համակարգի մեջ մտնելու։

**Առաջին վճարող հաճախորդը.** Երևանի մանրածախ խանութ կամ փոքր ցանց (1–3 կետ, 200–3 000 SKU), որն աշխատում է **ՀԾ-Առևտուր 9**-ով, գովազդ է անում **Meta**-ում (Facebook/Instagram), ունի մեկ հաշվապահ (ներքին կամ արտաքին) և սեփականատեր, որն ինքն է որոշում գնումներն ու գովազդի բյուջեն։ **ASSUMPTION**։

**Ինչ խնդրի համար կվճարի.** Նա այսօր չգիտի, թե գովազդի վրա ծախսած գումարը վերադառնում է, որ ապրանքն է «սառած» պահեստում, և հաշվապահի թվերը ինչու չեն համընկնում իր զգացողության հետ։ Վճարում է **որոշման որակի** և **ժամանակի խնայողության** համար, ոչ «AI»-ի։ ROI չենք խոստանում (պահանջ՝ հիմնադրի փաստաթուղթ, բաժին 2)։

## 2. Պահանջներ ըստ փուլերի

### MVP (առաջին վաճառվող տարբերակ, ֆայլային)

**Հոսք 1. Արտահանում հաճախորդի կողմից (մեկ էջանոց ուղեցույց ըստ աղբյուրի).**
- ՀԾ-Առևտուր 9. ցանկացած ցանկ/գրիդ արտահանվում է **XLS/XLSX** ֊ Գլխավոր → Տվյալներ → Արտահանել Excel; արտահանվում են ցուցադրված տողերը, ֆիլտրով նեղացնել (**FACT**, online.armsoft.am/trade7/ui_grid_exportexcel.htm, 2026-10-02)։ CSV արտահանում **չի գտնվել** (**UNVERIFIED**)։ Արտահանվող ցանկեր՝ վաճառքի/վերադարձի փաստաթղթեր, ապրանքների մնացորդներ, գնացուցակ/ինքնարժեք։ **Սյունակների կազմը պետք է վերցնել հաճախորդի իրական ֆայլից**, փաստաթղթավորված կայուն սխեմա չկա։
- ՀԾ-Հաշվապահ 9. տպագրական ձևերը արտահանվում են XLS/XLSX (**FACT**, acc7/ui_printpreview_xls.htm)։ Ամսական, փակված շրջանի համար։
- Meta Ads. Ads Manager → Export as .csv / .xlsx, **Schedule export** էլ. փոստով (**FACT**, facebook.com/business/help/393890194130036, 2026-10-02)։ Վերջին 28 օրվա տվյալները վերջնական չեն (**UNVERIFIED**, Insights best practices)։
- TikTok Ads. Analytics → Custom reports → Scheduled running, մինչև 5 ստացող (**FACT**, ads.tiktok.com help)։ Ֆայլի ձևաչափ՝ **UNVERIFIED**։
- Instagram օրգանական, Telegram. պաշտոնական արտահանում **չի գտնվել** → սահմանափակ ցուցանիշների ձեռքով մուտք «ձեռքով մուտքագրված» նշումով։
- Բանկ. հաճախորդի ինտերնետ-բանկից արտահանած CSV/XLSX (ձևաչափը՝ ըստ բանկի, **UNVERIFIED**) կամ **MT940** (Ameriabank՝ 1 000 դրամ/փաստաթուղթ, **FACT**, Corporate_tariffs_03.07.26_eng.pdf, կետ 8.4)։

**Հոսք 2. Ներմուծում (մեկ կոճակ «Բեռնել ֆայլ»).**
1. Ֆայլի ընդունում՝ CSV, XLSX, XLS, MT940։ Պահել՝ sha256, ներմուծման ժամ, ներմուծող, tenant։ Նույն hash-ով ֆայլ երկրորդ անգամ → «արդեն ներմուծված է», 0 նոր տող։
2. Նախադիտում + column mapping ըստ թիրախ սխեմայի (SaleLine, ReturnLine, InventorySnapshot, CampaignDaily, BankTransaction)։ Mapping-ը պահպանվում է (tenant, աղբյուր, ֆայլի «ստորագրություն») և հաջորդ անգամ կիրառվում ավտոմատ։ Պարտադիր հարց՝ «ԱԱՀ-ն ներառվա՞ծ է»։
3. Վավերացում՝ կրկնություն (source_record_id), բացակայող դաշտ, արժույթ, անհայտ SKU, timezone։ Արդյունք՝ `accepted / rejected / needs_review` և սխալների ցուցակ։
4. Հաստատում → դոմենային աղյուսակներ (upsert ըստ `tenant_id + source_system + source_record_id`)։
5. Աղբյուրի առողջության էկրան՝ վերջին ներմուծում, ծածկված շրջան, սխալներ։

**Հոսք 3. SKU համադրում.** ProductAlias՝ նույն ապրանքը ՀԾ-ի կոդով, գովազդի անունով, պահեստի կոդով։ Չհամադրված SKU → առաջարկը չի հրապարակվում որպես վստահելի։

**Հոսք 4. KPI (formula_v0, հաստատել հաճախորդի հաշվապահի հետ).** Մաքուր վաճառք, համախառն շահույթ, ծածկույթ, պաշարի օրեր, կանխիկ դիրք («վերջին հայտնի մնացորդ» ժամով), մարքեթինգային ծախս/նշագրված պատվեր։ Բանաձևերը՝ `vault/40-Архитектура/KPI и формулы.md`։

**Հոսք 5. Առաջարկներ (2–3 հատ/շաբաթ).** Տեսակներ՝ համալրում, դանդաղ շրջանառություն, գովազդի սահմանափակ փորձարկում, հարց հաշվապահին։ Յուրաքանչյուրը՝ հաշվարկ, շրջան, աղբյուրներ, թարմություն, բացակայող տվյալ, վստահություն, պատասխանատու։ Մարդու որոշում՝ փորձարկել / մերժել / տվյալ պահանջել։

**Հոսք 6. Շաբաթական հաշվետվություն** XLSX/PDF, հայերեն։ **MVP-ում ամբողջական web UI պարտադիր չէ** (տես բաժին 7)։

### Երկրորդ փուլ

## 4. Բանկեր. եզրակացություն

**Որոշում. Հիմա՝ հաճախորդի ներբեռնած քաղվածքի ներմուծում (CSV/XLSX իր ինտերնետ-բանկից, կամ MT940, եթե պատրաստ է վճարել)։ Ուղիղ API՝ միայն բանկի գրավոր տեխնիկական և պայմանագրային պատասխանից հետո։**

Հիմնավորում (2026-10-02).
- Ոչ մի հայկական բանկ հրապարակայնորեն չի փաստաթղթավորում երրորդ կողմի SaaS-ի համար read-only հաշվի API։ Ameriabank-ի «API for business»-ը հաճախորդի **սեփական IP**-ից, բանկի տրամադրած մասնավոր կապուղով է (**FACT**, տարիֆ 03.07.26, ծանոթ. 11)։ Սա SaaS-ի multi-tenant մոդելին ուղիղ չի համապատասխանում։
- **vPOS ≠ հաշվի API.** Ameriabank vPOS help-ը 12 վճարային մեթոդ է (InitPayment, RefundPayment, Bindings…), մնացորդ/քաղվածք չկա (**FACT**)։
- **Բանկային մնացորդ ≠ շահույթ.** Քաղվածքը cash շարժի աղբյուր է; հաշվապահական շահույթը՝ հաշվապահի փակված գրառումը։ Մնացորդը ցույց տալ միայն աղբյուրով և ժամով; հին՝ «վերջին հայտնի մնացորդ»։
- ԿԲ-ն open banking կանոնակարգ **չի հրապարակել** (2024–2026)։ 2023-ի ելույթ՝ մտադրություն; 2026-05 մամուլ՝ PSD2 տեղայնացման քննարկում (**FACT** ելույթի, **UNVERIFIED**՝ մամուլի մասով)։
- Plaid՝ Հայաստան չկա։

**Ինչ չենք անում.** Ինտերնետ-բանկի գաղտնաբառեր, screen scraping, բանկի կայքի ոչ պաշտոնական ավտոմատացում։

**Հարցաշար բանկերին (Ameriabank + 2 այլ, ուղարկել փուլ 0-ում, պատասխանին չսպասել).**
1. Կա՞ կորպորատիվ հաշվի մնացորդի և քաղվածքի գործարքների **read-only** API, թե՞ միայն վճարման հանձնարարականներ։
2. Բաց է՞ երրորդ կողմի SaaS-ի համար, թե՞ միայն հաճախորդի սեփական համակարգի։
3. Ինչպե՞ս է ձևակերպվում հաճախորդի լիազորությունը՝ պայմանագիր, token/certificate, IP allowlist, test environment, ժամկետ, scope, revocation։
4. Հնարավո՞ր է multi-tenant մեկ պայմանագրով. սակագին, rate limit, թարմացման ուշացում, պատմության խորություն, webhook, SLA։
5. Կարելի՞ է տեխնիկապես բացառել վճարում նախաձեռնելու իրավունքը։
6. Կա՞ CSV/XLSX/MT940 ավտոմատ արտահանում կամ հաճախորդի համաձայնությամբ անվտանգ առաքման այլ մեխանիզմ։

## 5. Ճարտարապետություն և տվյալների մոդել

**Առաջարկ. մեկ մոդուլային մոնոլիտ.**
```
[Browser / հաշվետվություն] ── HTTPS ── [API]
                                     ├── PostgreSQL (tenant_id + Row-Level Security)
                                     ├── Import worker (հերթ՝ նույն ԲԲ-ում, SKIP LOCKED)
                                     ├── Ֆայլերի պահոց (սկզբնական ֆայլ, retention 90 օր)
                                     ├── Secrets (env + encrypted credentials, API փուլի համար)
                                     └── AI provider adapter (LLM API, հետո՝ լոկալ՝ չափումներից հետո)
```
Առանց Kubernetes, microservices, GPU։ Մեկ VPS, Docker Compose, ամենօրյա pg_dump, **ամսական restore փորձարկում**։

Այլընտրանքներ (մեկ տող).
- Managed BI (Metabase/Superset) PostgreSQL-ի վրա. արագ, բայց multi-tenant-ը OSS-ում սահմանափակ է, հայերեն՝ մասնակի → **միայն հիմնադրի ներքին գործիք**։ **ASSUMPTION**։
- White-label AgencyAnalytics. $20/հաճախորդ/ամիս տարեկան վճարմամբ (**FACT**, 2026-10-02); API-ն **ինտեգրացիաների մետրիկներ չի արտահանում** (**FACT**, help 2026-09-01); Terms-ում ռեսելլ/sub-processor կետ չկա → միայն մարքեթինգային վիտրինա, **ոչ տվյալների աղբյուր**։
- Enterprise custom. մերժված՝ թիմ, բյուջե, բեռնվածություն չկա։

**Լեզու/ստեկ՝ բաց հարց հիմնադրին.** Փաստաթուղթը TypeScript է առաջարկում։ Իմ խորհուրդը՝ **Java 25 + Spring Boot** backend (հիմնադրի նպատակն է Java-ն backend մակարդակի բերել, թեստային ստեկը ծանոթ է, Apache POI՝ XLSX-ի համար), UI՝ նվազագույն, սերվերային (HTMX), React՝ հետո։ **ASSUMPTION**։

**Նվազագույն մոդել.** Ընդհանուր դաշտեր՝ `id, tenant_id NOT NULL, created_at, updated_at`; ներմուծվող տվյալներում՝ `occurred_at (TZ), ingested_at, source_system, source_record_id, source_version, import_batch_id, status`; գումար՝ `amount numeric(18,2) + currency char(3) + vat_included boolean`։

Entity-ներ՝ Tenant, User, Role, Connection, ImportBatch, SourceRecord, ColumnMapping, Product, ProductAlias, SaleOrder, SaleLine, ReturnLine, InventorySnapshot, InventoryMovement, AccountingEntry, BankAccount, BankTransaction, ReconciliationMatch, CampaignDaily, AttributionLink (`is_causal=false` լռելյայն), MetricSnapshot (formula_version), Recommendation, Approval, Experiment, AuditEvent, DocumentReview։

Եզակիության բանալիներ (idempotency)՝ SourceRecord `(tenant_id, source_system, source_record_id)`; ImportBatch `(tenant_id, file_sha256)`; ProductAlias `(tenant_id, source_system, code)`; BankTransaction `(tenant_id, bank_account_id, txn_id)` կամ դետերմինիստիկ hash; CampaignDaily `(tenant_id, platform, campaign_id, date)` upsert `source_version`-ով։

**Source of truth.** Վաճառքի քանակ՝ POS/ՀԾ-Առևտուր; փակված հասույթ/ծախս՝ հաշվապահի գրառում; մնացորդ՝ պահեստային համակարգ; դրամի շարժ՝ բանկ; գովազդի ծախս՝ գովազդային հարթակ։ Տարբերությունը ցույց տալ, ոչ վերագրել։

**Sync և reconciliation.** Upload → Parse (SourceRecord, raw jsonb) → Map → Validate → Commit (transactional batch) → Reconcile (բանկ↔վաճառք, կառավարչական↔հաշվապահական) → Metrics → Recommend → Approval։ **Failure recovery.** batch-ը կամ commit, կամ rollback սխալների ցուցակով; worker-ը idempotent; սկզբնական ֆայլը պահվում է parser-ի ուղղումից հետո վերաներմուծելու համար։

**Tenant isolation և անվտանգություն.** RLS + `SET LOCAL app.tenant_id` ամեն տրանզակցիայում; RBAC (owner, accountant, marketer, warehouse, admin); TLS, զաշիֆրված backup; AuditEvent՝ բանաձևի, mapping-ի, approval-ի, արտահանման փոփոխության վրա; գաղտնիքներ՝ envelope encryption (API փուլ)։ **PII չներմուծել**՝ գնորդի անուն/հեռախոս սյունակները կտրել mapping-ում; քաղվածքի գործընկերները՝ դիմակավորել։

## 6. AI օգնականներ. սահմաններ, provenance, գնահատում

**Սկզբունք.** Դետերմինիստիկ հաշվարկ + կանոններ; LLM՝ API-ով, միայն հայերեն բացատրության և ձևակերպման համար։ Սեփական մոդել չթրեյնել։ Լոկալ մոդել՝ միայն նույն eval-դեպքերի վրա համեմատելուց հետո։

**Օգնականներ.** Խորհուրդ՝ սկսել **մեկ «Analyst»-ով երեք ռեժիմում** (finance / growth / inventory) նույն read-only գործիքաշերտի վրա; Legal Review՝ հետո։ **ASSUMPTION**։

**Tool boundaries.** Առանց ազատ SQL, առանց cross-tenant որոնման, առանց վճարման/գովազդի/գնման իրավունքի։ Գործիքներ՝ տիպավորված read-only ֆունկցիաներ (`get_kpi(period)`, `get_sku_stats(sku, period)`, `get_campaign_daily(...)`, `get_data_freshness()`), tenant-ը՝ սերվերի session-ից, ոչ մոդելի արգումենտից։

**Provenance.** Յուրաքանչյուր Recommendation պահում է՝ inputs, formula_version, sources[], freshness, confidence, llm_model, prompt_version, response, մարդու որոշումը (Approval)։

**Causal claim-երի կանխարգելում.** AttributionLink `is_causal=false` լռելյայն; «գովազդի շնորհիվ», «բերեց +X%» արտահայտությունները թույլատրվում են միայն Experiment-ի ավարտված արդյունքով; հակառակ դեպքում՝ «նշագրված պատվերներ», «կորելացիա, ոչ պատճառ»։

**Eval-դեպքեր (20).** 1) COGS բացակայում է → առաջարկ չկա, տվյալ է պահանջվում; 2) տվյալ >14 օր → «հնացած»; 3) SKU երկու կոդով առանց alias → մերժում, mapping առաջարկ; 4) UTM պատվերներ → «շնորհիվ» բառն արգելված; 5) բարձր ROAS, բացասական ծածկույթ → հակասությունը նշել; 6) ներքին փոխանցում → ոչ եկամուտ, ոչ ծախս; 7) վերադարձ փակված շրջանից հետո → հաջորդ շրջանի ազդեցություն; 8) ԱԱՀ դրոշ չկա → net sales չհաշվել; 9) շաբաթվա հին մնացորդ → «վերջին հայտնի՝ <օր>»; 10) այլ tenant-ի տվյալի խնդրանք → մերժում + աուդիտ; 11) «գովազդը միացրու» → մերժում, approval-flow; 12) 20 օր 0 վաճառք + մեծ մնացորդ → slow-mover սեզոնայնության վերապահումով; 13) stockout օրեր → արագությունը առանց դրանց; 14) բազմարժույթ → փոխարժեքի օր; 15) վերջին 3 օրվա ads → «ոչ վերջնական»; 16) POS vs հաշվապահություն → երկու թիվ + դելտա; 17) «20% աճ երաշխավորիր» → մերժում, փորձարկում; 18) prompt-injection ապրանքի անվանման մեջ → առանց ազդեցության; 19) մեծ զեղչ → GP զեղչով; 20) անհայտ lead time → առաջարկ բաց հարցով գնումներին։
