# Claude-ի առաջադրանք. մանրածախ բիզնեսի AI վերլուծական հարթակ

**Փաստերի ստուգման օր՝ 2026-09-29։** Այս ֆայլը նախատեսված է ամբողջությամբ Claude-ին տալու համար։ Այն ինքնաբավ նախագծային կոնտեքստ է և վերջում պարունակում է կոնկրետ առաջադրանքը։ Եթե որևէ արտաքին հղում այլևս չի աշխատում, դա նշիր և մի ներկայացրու տվյալ հնարավորությունը որպես հաստատված։

## 1. Հիմնադրի նպատակը և սահմանափակումները

Ես ապրում եմ Երևանում։ Ուզում եմ հիմնել B2B ծառայություն և հետագայում սեփական SaaS հարթակ, որը Հայաստանի փոքր ու միջին մանրածախ բիզնեսներին օգնում է **ավելացնել շահութաբեր վաճառքը**։ Սկզբնական կանխիկ բյուջեն առավելագույնը մոտ $1,000 է. դա չի ներառում իմ աշխատանքի արժեքը կամ ամբողջական ծրագրային մշակում պատվիրելու բյուջե։ Ես ունեմ API, տվյալների բազաների, QA ավտոմատացման, թեստավորման և տեխնիկական նախագծերի համակարգման փորձ։ Առաջին վճարող հաճախորդներից հետո կվերաներդնեմ հասույթը։

**Հիմնադրի վերջին և գերակա որոշումը. առաջինը նախագծել հաճախորդի կողմից տվյալների արտահանման/ներբեռնման և մեր հարթակ ֆայլերի ներմուծման տարբերակը։** ՀԾ, գովազդային հարթակ կամ բանկ ուղիղ միանալու հնարավորությունները ուսումնասիրել որպես հաջորդ փուլ։ Ոչ մի ավտոմատ API միացում առաջին վաճառվող տարբերակի պարտադիր պայման չէ։ Երբ պարզվի, որ որևէ աղբյուրից ֆայլ վերցնելն անհնար է կամ տվյալը պակաս է, հենց այդ աղբյուրի այլ թույլատրված ուղին առանձին ուսումնասիրել։ Ավտոմատացումը նախապատվություն կստանա, երբ ֆայլային տարբերակը ցույց տա հաճախորդի վճարելու պատրաստակամությունը և ձեռքով աշխատանքի իրական արժեքը։

Նախորդ քննարկմամբ առաջին հաճախորդների սեգմենտն ընտրվել է **մանրածախ առևտուրը**՝ ապրանքների կոդերով, վաճառքով, ինքնարժեքով, պահեստով և գովազդով։ «Բոլոր կազմակերպությունների» աջակցությունն ապագա ընդլայնումն է։ Առաջին վաճառվող տարբերակն անհրաժեշտ է նախագծել մի նեղ սեգմենտի համար։

Արդեն պատրաստվել է դիտելի, մեկ HTML ֆայլից բաղկացած «Առևտրաչափ» հայերեն ցուցադրական նախատիպ՝ գլխավոր էջ, ապրանքներ/պահեստ, մարքեթինգ, առաջարկներ, ֆինանսներ, իրավաբան և տվյալների աղբյուրներ։ Նրա թվերը օրինակային են, իրական API միացում չունի։ Եթե ֆայլը կցված չէ այս խոսակցությանը, մի ձևացրու, թե տեսել ես այն. ստորև նկարագրված պահանջներն ինքնաբավ են։

## 2. Պրոդուկտի խոստումը

Սեփականատերը մեկ տեղում տեսնում է վաճառք, ապրանքային շահույթ, պահեստ, մարքեթինգային ծախս, դրամական շարժ և հաշվապահական համապատասխանեցման վիճակ։ Համակարգը առաջարկում է՝ ինչ ապրանք համալրել, ինչի գովազդը փոքր բյուջեով փորձարկել, ինչը վերանայել և ինչ հարց տալ հաշվապահին։ Յուրաքանչյուր առաջարկը ցույց է տալիս հաշվարկը, ժամանակահատվածը, աղբյուրները, տվյալների թարմությունը, բացակայող տեղեկությունը, վստահության աստիճանը և պատասխանատու մարդուն։

Այն չի երաշխավորում վաճառքի աճ։ Նպատակն է չափելիորեն բարելավել որոշումների որակը և, փորձարկումներով հաստատելու դեպքում, հավելյալ ծածկույթի/շահույթի չափը։

## 3. Օգտատերեր և գործնական հոսքեր

| Դեր | Տեսնում է | Կարող է անել |
| --- | --- | --- |
| Սեփականատեր/տնօրեն | Գլխավոր KPI-ներ, եկամուտ, ծածկույթ, բանկի վերջին հայտնի մնացորդ, ռիսկեր | Հաստատել գործողության ծրագիրը, նշանակել պատասխանատու, չափել արդյունքը |
| Հաշվապահ/ֆինանսիստ | Վաճառք, վերադարձ, COGS, ծախսեր, հաշիվների ու բանկի համադրում | Հաստատել հաշվարկի կանոնները, փակել հաշվետու ամիսը, բացատրել անհամապատասխանությունները |
| Մարքեթոլոգ | Ալիք/արշավ/ապրանքային խմբի ծախս, նշագրված պատվերներ | Նախագծել և հաստատել սահմանափակ փորձարկում. գովազդ միացնել միայն առանձին լիազորությամբ |
| Պահեստի/գնումների ղեկավար | SKU, մնացորդ, վաճառքի արագություն, բաց պատվեր | Ստուգել համալրման առաջարկը և մատակարարման ժամկետը |
| Իրավաբան՝ հետագա փուլ | Պայմանագրի նախագիծ, տվյալների մշակման պայմաններ, գովազդային խոստումներ | Մեկնաբանել ու հաստատել վերջնական իրավական տեքստը |
| Հարթակի ադմինիստրատոր | Հաճախորդների միացումների առողջություն, վճարում, տեխնիկական իրադարձություններ | Միայն իրեն անհրաժեշտ նվազագույն հասանելիություն՝ աուդիտով |

Առաջին աշխատանքային սցենար. հաճախորդը տալիս է 90 օրվա վաճառքի և վերադարձի տողեր, ապրանքների կոդեր/ինքնարժեք, պահեստի մնացորդներ, գովազդի ծախսերի արտահանում և կամընտիր բանկային քաղվածք։ Ծրագիրը ներմուծում է, ստուգում, համադրում, ցույց է տալիս սխալները, հաշվում KPI-ները, տալիս է 2–3 քննարկելի առաջարկ։ Մարդը որոշում է՝ փորձարկել, մերժել, թե լրացուցիչ տվյալ պահանջել։ Հետո չափվում է արդյունքը։

### Առաջին տարբերակի ֆայլային ներմուծման հոսք

1. Հաճախորդին տալ ըստ աղբյուրի մեկ էջանոց ուղեցույց՝ որտեղից և ինչ ժամանակահատվածի տվյալ արտահանել, ինչ ձևաչափով և ինչ նվազագույն սյունակներով։ ՀԾ-ի, Meta-ի և բանկի ճշգրիտ էկրանի քայլերը ստուգել տվյալ հաճախորդի տարբերակում. չհորինել ընդհանուր UI հրահանգ։
2. Ընդունել CSV/XLSX, բանկի դեպքում նաև MT940, եթե հասանելի է։ Սկզբում պահպանել սկզբնական ֆայլը սահմանափակ ժամկետով ու անհրաժեշտ իրավունքներով, ներմուծման ամսաթիվը, ֆայլի hash-ը և ներմուծողի անունը։ PDF/նկարից OCR-ը առաջին տարբերակի հիմք չդարձնել։
3. Տալ նախադիտում և column mapping՝ պատվերի ID, ամսաթիվ/ժամ, SKU, քանակ, մաքուր գին, զեղչ, վերադարձ, ինքնարժեք, պահեստ, արշավ/ծախս, բանկային գործարքի ID/գումար/արժույթ/մնացորդ։ Առանձին նշվի՝ ԱԱՀ-ն ներառվա՞ծ է։
4. Ստուգել կրկնությունները, բացակայող դաշտերը, սխալ արժույթը և չհամընկնող SKU-ները։ Ներմուծումը կամ հաստատվում է սխալների ցուցակով, կամ վերադարձվում է ուղղման. նույն ֆայլը երկրորդ անգամ բեռնելը չպետք է կրկնապատկի վաճառքը։
5. Առաջին ներմուծմամբ վերցնել մոտ 90 օր պատմություն, հետո պայմանավորվել շաբաթական նոր արտահանման մասին. վահանակում միշտ ցույց տալ յուրաքանչյուր աղբյուրի վերջին թարմացման ժամանակը։
6. Եթե սոցցանցը տվյալ հաշվից արտահանման հնարավորություն չի տալիս, թույլատրել սահմանափակ ցուցանիշների ձեռքով լրացում՝ հստակ «ձեռքով մուտքագրված» նշումով։ Եթե բանկի ֆայլը հասանելի չէ, չցուցադրել ենթադրյալ «ընթացիկ մնացորդ»։

## 4. Ինտեգրացիաների փաստացի քարտեզ

Կարգավիճակները. **Փաստաթղթավորված** = պաշտոնական փաստաթուղթը հաստատում է համապատասխան API-ն կամ արտահանման ձևը, բայց կոնկրետ հաճախորդի իրավունքը դեռ ստուգման կարիք ունի։ **Պայմանական** = կա տեխնիկական ուղի, բայց պետք են հավելյալ հաստատում/պայմանագիր/հաճախորդի իրավասություն։ **Չհաստատված** = տվյալ կարողությունը կամ երրորդ կողմի հասանելիությունը պաշտոնական աղբյուրով դեռ չի ապացուցվել։

## 5. Բանկային մասի հատուկ հետազոտական առաջադրանք

Ամերիաբանկի [2026-04-03-ից գործող կորպորատիվ սակագնում](https://ameriabank.am/Portals/0/files/Business/green/Corporate_tariffs_03.04.26_eng.pdf) նշված է «Internet Banking API for business»՝ տարեկան 40,000 դրամ, և MT940 քաղվածքի տրամադրում՝ 1,000 դրամ մեկ փաստաթղթի համար։ Սա **չի հաստատում**, թե անկախ SaaS ընկերությանը բաց են account balance/transactions read-only endpoint-ները կամ արդյոք մեկ պայմանագրով կարելի է սպասարկել բազմաթիվ ընկերությունների։ Բանկի [vPOS API](https://servicestest.ameriabank.am/VPOS/help) հրապարակային նկարագրությունը վերաբերում է վճարումների և վերադարձների գործողություններին։

Առաջարկիր Ամերիաբանկին և 2 այլ առաջնահերթ հայկական բանկի ուղղվող հարցաշար, բայց մյուս բանկերի API-ն փաստ մի համարիր՝ առանց պաշտոնական ապացույցի.

- Կա՞ corporate account balance և statement transaction read-only API, թե՞ միայն վճարման պատվերներ։
- Բաց է՞ երրորդ կողմի SaaS-ին, թե՞ միայն բանկի ուղղակի կորպորատիվ հաճախորդի համակարգին։
- Ինչպե՞ս է տրվում հաճախորդի լիազորությունը. առանձին պայմանագիր, token/certificate, IP allowlist, test environment, ժամկետ, scope և revocation։
- Հնարավո՞ր են մի քանի tenant-ներ, ինչպիսի՞ն են սակագինը, rate limit-ը, թարմացման ուշացումը, պատմական խորությունը, webhook-ը և աջակցության SLA-ն։
- Արդյոք կարելի՞ է միայն ընթերցել և տեխնիկապես բացառել վճարում նախաձեռնելու իրավունքը։
- Առկա՞ են CSV/XLSX/MT940 ավտոմատ արտահանումներ կամ հաճախորդի համաձայնությամբ անվտանգ առաքման այլ մեխանիզմ։

Ոչ մի փուլում մի առաջարկիր հաճախորդի internet banking գաղտնաբառերի հավաքում, screen scraping կամ բանկի կայքի ոչ պաշտոնական ավտոմատացում։ Քաղվածքը դիտարկել որպես cash շարժի աղբյուր, իսկ ոչ ինքնաբերաբար հաշվապահական շահույթի ճշմարտություն։ Բանկի փաստացի մնացորդը ցույց տուր միայն աղբյուրի և թարմացման ժամանակի հետ. եթե այն հին է, գրիր «վերջին հայտնի մնացորդ»։

## 6. Տվյալների մոդել և ճշմարտության աղբյուրներ

Նախագծիր multi-tenant SaaS՝ կազմակերպությունը որպես tenant, առանձին խանութներ/պահեստներ/բանկային հաշիվներ և յուրաքանչյուր տողի տվյալների ծագում։

Նվազագույն հիմնական entity-ներ՝ Tenant, User, Role, Connection, ImportBatch, SourceRecord, Product, ProductAlias/Mapping, SaleOrder, SaleLine, ReturnLine, InventorySnapshot, InventoryMovement, AccountingEntry/Expense, CampaignDaily, AttributionLink, BankAccount, BankTransaction, ReconciliationMatch, MetricSnapshot, Recommendation, Approval, Experiment, AuditEvent, DocumentReview։ Նշիր mandatory բանալիները, currency, tenant_id, occurred_at, ingested_at, source_system, source_record_id, source_version և status դաշտերը։

Սկզբնաղբյուրների գերակայություն. ապրանքների օպերացիոն վաճառքի քանակը՝ POS/Trade, հաշվապահական փակված հասույթն ու ծախսը՝ հաշվապահության հաստատված գրառում, պահեստի առկա քանակը՝ համապատասխան պահեստային համակարգ, դրամի փաստացի շարժը՝ բանկային քաղվածք, գովազդի ծախսը՝ գովազդային հարթակ։ Եթե դրանք տարբերվում են, ցույց տուր տարբերությունը և բացատրության հերթը. մի ջնջիր կամ լուռ վերագրիր տվյալը։

Տվյալների որակի ստուգումներ՝ կրկնվող փաստաթուղթ, վերադարձների նշան, նույն SKU-ի տարբեր կոդեր, միավորների տարբերություն, timezone, ԱԱՀ ներառյալ/առանց ԱԱՀ, բազմարժույթ փոխարժեքի օր, անկատար էջավորում, source gap, գովազդի վերջնականացումից առաջ տվյալների ուշացում, հաշվապահական փակման ամսաթիվ, բանկային ներսային փոխանցումների կրկնակի հաշվարկ։

## 7. KPI-ներ և ֆինանսական տրամաբանություն

Սկզբում հաշվապահի հետ ֆիքսել բանաձևերը և tax basis-ը։ Նախնական կառավարման ցուցանիշներ.

- Մաքուր վաճառք = վաճառքի գումար − զեղչ − վերադարձ, առանց ԱԱՀ, եթե այդպես հաստատված է կազմակերպության հաշվառմամբ։
- Համախառն շահույթ = մաքուր վաճառք − վաճառված ապրանքի փաստացի ինքնարժեք (COGS)։
- Ծածկույթ = համախառն շահույթ − պատվերից կախված առաքում/վճարային միջնորդավճար/վերադարձի ծախս − տվյալ շրջանի գովազդային ծախս։ SKU-ով գովազդի բաշխումը ցույց տալ որպես **բաշխման մեթոդ**, ոչ փաստ, եթե ուղղակի կապ չկա։
- Կանխիկ դիրք = բանկային հաստատված մնացորդներ + դրամարկղային հաստատված մնացորդ՝ կոնկրետ ժամի դրությամբ. սա նույնը չէ, ինչ շահույթ կամ ազատ ծախսելի գումար։
- Պաշարի օրեր = հասանելի մնացորդ ÷ վերջին համապատասխան շրջանի օրական վաճառքի արագություն, հաշվի առնելով զրոյական պահանջարկը, սեզոնայնությունն ու stockout օրերը։
- Մարքեթինգ՝ ծախս, նշագրված պատվեր, դրանց հաշվարկային արժեք։ ROAS-ը և UTM նշագրումը չեն ապացուցում **հավելյալ** վաճառք։ Պատճառահետևանքը չափել փոքր վերահսկվող փորձարկմամբ, երբ հնարավոր է։
- Հաճախորդի համար արդյունքի չափիչ՝ փորձարկման հետևանքով հավանական հավելյալ ծածկույթ, տվյալների վստահելիություն, և կատարած գործողությունների բաժին։ Ֆիքսված ROI խոստում մի ձևակերպիր։

Օրինակային AI առաջարկը պետք է լինի այս տեսքի՝ «SKU B-ի մաքուր գինը 35,000 դրամ է, ինքնարժեքը 22,000 դրամ, 126 հատ մնացորդ կա։ Եթե առաքումն ու վերադարձի պահուստը միասին 2,000 դրամ/հատ են, մինչև գովազդը մնում է մոտ 11,000 դրամ։ Առաջարկել սահմանափակ փորձարկում և թիրախային ձեռքբերման արժեքի շեմ, սակայն այդ 2,000 դրամը ենթադրություն է. հաստատի՛ր հաշվապահի հետ»։

## 8. AI-ի և գործակալների սահմանները

Պետք չէ սկզբում սեփական մոդել թրեյն անել։ Առաջին փուլ՝ deterministic հաշվարկներ + կանոններ + API-ով օգտագործվող LLM հայերեն բացատրությունների համար։ Լոկալ մոդել դիտարկել, երբ պարզ լինի գաղտնիության, տվյալների բնակության, հաճախորդի պահանջի և մեկ հարցման ինքնարժեքի իրական առավելությունը։ Համեմատել նույն փորձնական դեպքերի վրա։

Նախագծիր ոչ ավելի քան չորս սահմանափակ օգնական.

1. **Finance Analyst**՝ միայն հաստատված aggregate KPI, P&L համադրում և «տվյալը բավարար չէ» վիճակ։
2. **Growth Analyst**՝ արշավների համեմատություն, փորձարկման նախագիծ, attribution-ի սահմանների նշում։
3. **Inventory Analyst**՝ համալրման/դանդաղ շրջանառության ազդակներ՝ մատակարարման ժամկետի բացակայությունը նշելով։
4. **Legal Review Assistant՝ հետագայում**՝ պայմանագրի կամ գովազդային տեքստի նախագծի ստուգման կետեր, վերջնական խոսքը՝ իրավաբանին։

Գործակալներին չտալ ազատ SQL, բոլոր tenant-ների որոնում, բանկային փոխանցման կամ գովազդային փոփոխության ինքնուրույն իրավասություն։ Նրանց գործիքները լինեն սահմանափակ read-only API-ներ, որտեղ tenant-ը ստուգվում է սերվերում։ Յուրաքանչյուր առաջարկ պահի հաշվարկի մուտքերը/տարբերակը, աղբյուրները, AI պատասխանի տարբերակը և մարդու որոշումը։ Ոչ մի գործակալ չի ստեղծում վճարում, գովազդ, գնում կամ իրավական պարտավորություն առանց առանձին հաստատված աշխատանքային հոսքի։

## 9. Ճարտարապետություն, անվտանգություն և իրավական հիմք

Քննարկիր մեկ պարզ modular web app (օրինակ՝ TypeScript UI/API + PostgreSQL + հերթագրված ներմուծման worker + գաղտնիքների ապահով պահոց + AI provider adapter)՝ երկու այլընտրանքի հետ՝ managed BI/white-label pilot և ավելորդ մեծ ծավալով custom enterprise կառուցում։ Տեխնոլոգիան ընտրիր ըստ իմ թիմի կարողության և $1,000 կանխիկ սահմանի. microservices/Kubernetes/սեփական GPU չառաջարկել առանց անհրաժեշտության։

Հաճախորդների բաժանում՝ tenant_id ամեն entity-ում, DB-ում row-level isolation կամ համարժեք ստուգվող մեխանիզմ, RBAC, հաշվապահի ու սեփականատիրոջ տարբեր իրավունքներ, գաղտնիքների շտեմարան, encryption, audit log, backup/restore փորձարկում, retention/deletion և պայմանագրով տվյալների արտահանում։ Սկզբում միայն read-only ինտեգրացիաներ։ Ստեղծել կապի առողջության էկրան՝ վերջին sync, սխալ, միջակայք, permissions և credential expiry։

ՀՀ [անձնական տվյալների պաշտպանության գործող օրենքի](https://www.arlis.am/hy/acts/218690) 5-րդ հոդվածը պահանջում է տվյալների նվազագույն և նպատակին համաչափ մշակում, 27-րդ հոդվածը կարգավորում է այլ պետություններ փոխանցումը։ Որոշիր՝ ինչն է իրականում անձնական տվյալ, ովքեր են մշակող/լիազորված, որտեղ են պահվում տվյալները և ում են փոխանցվում։ Իրավաբանի եզրակացություն պահանջիր մինչև իրական հաճախորդների անձնական տվյալների արտասահմանյան մատակարարին փոխանցելը։ Արտասահման վաճառելու դեպքում յուրաքանչյուր շուկայի լրացուցիչ պահանջները ստուգել առանձին։

Եթե օգտագործվի [AgencyAnalytics-ի white-label համակարգը](https://agencyanalytics.com/pricing), նրա հրապարակված սկզբնական գինը 2026-09-29-ին $20/հաճախորդ/ամիս էր տարեկան վճարմամբ։ Այն կարող է օգնել մարքեթինգային ցուցադրմանը, բայց սեփական SKU/ֆինանսական տրամաբանության հիմնական աղբյուրը չպետք է կախված լինի չապացուցված data-export իրավունքից։ [Օգտագործման պայմանների](https://agencyanalytics.com/company/terms) ձևակերպման և վերավաճառքի/ենթակատարողի կոնկրետ սցենարի վերաբերյալ անհրաժեշտ է մատակարարի գրավոր հաստատում։ Հաճախորդի պայմանագիրը պետք է ճիշտ նկարագրի տվյալների մշակման ենթակատարողներին և պատասխանատվությունը. հանրային նյութում կարելի է շեշտել սեփական ապրանքանիշը, բայց չհայտարարել, թե բոլոր արտաքին համակարգերն ու մոդելը սեփական մշակման են։

## 10. Իրագործման առաջարկվող հերթը՝ Claude-ը պետք է քննադատի և բարելավի

**Փուլ 0, 1–2 շաբաթ.** Հարցազրույց 5 մանրածախ կազմակերպության հետ, մեկ կոնկրետ POS/ՀԾ տարբերակի ընտրություն, արտահանվող ֆայլերի օրինակների ձեռքբերում, 2 վճարովի փորձնական առաջարկ։ Կնքել տվյալների հասանելիության/գաղտնիության պայմաններ։ Չգնել տարեկան ծրագրեր մինչև փաստացի հաճախորդի կարիքը պարզ լինի։

**Փուլ 1, 2–4 շաբաթ.** CSV/Excel ներմուծում՝ վաճառք, վերադարձ, SKU, ինքնարժեք, մնացորդ, Meta spend, կամընտիր բանկի քաղվածք։ SKU mapping, տվյալների որակի սխալների էկրան, ձեռքով հաստատվող KPI, 2–3 աղբյուրով հիմնավորված առաջարկ և շաբաթական հաշվետվություն։ Առաջին վաճառվող ծառայությունը կարող է ունենալ ձեռքով ստուգվող բաղադրիչ։

**Փուլ 2, 1–3 ամիս.** Հաճախորդների առանձին հաշիվներ, role-եր, կրկնվող ֆայլային ներմուծման հարմարեցում, import errors և քաղվածքի համապատասխանեցում։ Առաջին վճարող հաճախորդների աշխատանքից հետո որոշել՝ ՀԾ-ի կամ Meta-ի ո՞ր մեկ read-only API միացումն է իրականում փոխհատուցում արժեքը։ Եթե ձեռքով արտահանումը բավարար է, ավտոմատացումը հետաձգել։

**Փուլ 3, 3–6 ամիս.** Ըստ ապացուցված պահանջի read-only ՀԾ կամ Meta միացում, Shopify/WooCommerce կամ TikTok՝ կոնկրետ հաճախորդի կարիքի և հասանելիության դեպքում, փորձարկումների հետևում, հաճախորդների ինքնասպասարկում։ Բանկի ուղիղ API՝ միայն բանկի հետ գրավոր տեխնիկական և իրավական համաձայնությունից հետո։

**Փուլ 4, 6–12 ամիս.** Անգլերեն/ռուսերեն, բազմարժույթ, Xero/QuickBooks adapter, արտահանվող localization/tax կանոններ, միջազգային առաջին վճարող հաճախորդ։ Լոկալ AI մոդելի որոշում միայն չափումներից հետո։

Սա ժամանակի հիպոթեզ է՝ կախված թիմից և API հաստատումներից։ Հեռացնել ժամկետային անհիմն խոստումները։

## 11. Պարտադիր ստուգումներ և ընդունման չափանիշներ

- CSV և API նույն փաստաթղթի ներմուծումը կրկնելիս կրկնակի վաճառք չի ստեղծվում։
- Վերադարձը, զեղչը, ԱԱՀ-ն, արժույթը, rounding-ը և բացասական մնացորդը ճիշտ են մշակվում։
- Առաջարկը չի հրապարակվում որպես վստահելի, երբ ինքնարժեքը բացակայում է, աղբյուրը հին է կամ SKU mapping-ը անհստակ է։
- Փակված շրջանի կառավարման վաճառքը համադրվում է հաշվապահի հաստատած հաշվետվության հետ. տարբերությունը երևում է՝ թվային բացատրությամբ։
- Նույն հաճախորդի բանկային փոխանցումը սեփական երկու հաշիվների միջև կրկնակի եկամուտ/ծախս չի դառնում։
- Մարքեթինգի AI-ը չի կոչում նշագրված պատվերները «գովազդի շնորհիվ հավելյալ վաճառք» առանց փորձարկման։
- Մեկ tenant-ի օգտվողը չի կարող API/UI/AI միջոցով տեսնել մյուսի տվյալները։
- Միացումների 401/403, rate limit, pagination, token expiry, մասնակի ձախողում, հետին թվով ճշգրտում, timezone և ուշացող ads reports ստուգված են։
- Արտաքին գործողություններն ունեն owner, approval, audit, rollback/կասեցման միջոց։ Առաջին փուլում դրանք ավտոմատ չեն։

## 12. Բիզնես մոդել և սահմաններ

Առաջին գների աշխատանքային հիպոթեզ՝ 120–250 հազար դրամ միացում և 79–149 հազար դրամ ամսական ըստ տվյալների աղբյուրների և մարդկային վերլուծության ծավալի։ Սրանք ստուգված շուկայական գներ չեն։ Հաշվիր software/API/bank/hosting/model/աշխատաժամերի/աջակցության ամբողջական ինքնարժեքը, gross margin-ը և հաճախորդ ձեռք բերելու արժեքը առնվազն երեք սցենարով։ $1,000 կանխիկը պետք է ծախսվի վաճառվող փորձարկման, ոչ լրիվ ավտոմատացված SaaS-ի վրա։ Մարքեթինգային կառավարումը և իրավաբանի ծառայությունը առանձին պայմանագրերով/գներով են։

## 13. ՔՈ ՀԻՄԱ ԿԱՏԱՐԵԼԻՔ ԿՈՆԿՐԵՏ ԱՌԱՋԱԴՐԱՆՔԸ

Գործիր որպես B2B SaaS product manager, տվյալների/AI համակարգի ճարտարապետ, ֆինանսական վերլուծաբան և ինտեգրացիաների տեխնիկական հետազոտող։ Մի հորինիր անձնական մասնագիտական փորձ կամ մատակարարների թույլտվություններ։ Այս փաստաթուղթը դիտարկիր որպես հիմնադրի կոնտեքստ և հետազոտության մեկնարկային ցուցակ, ոչ անվիճելի ճշմարտություն։

Եթե ունես վեբ հասանելիություն՝ ստուգիր 2026 թվականի **ընթացիկ պաշտոնական** API փաստաթղթերը, սակագները, հասանելիության/վերավաճառքի պայմանները և ՀՀ օրենքի գործող խմբագրությունը։ Եթե վեբ հասանելիություն չկա՝ այս հղումները նշիր որպես 2026-09-29-ի տվյալներով նախնական աղբյուրներ, և չստուգված մասերը մի հաստատիր։ Տարանջատիր **ՓԱՍՏ / ԵՆԹԱԴՐՈՒԹՅՈՒՆ / ՉՍՏՈՒԳՎԱԾ / ՊԱՅՄԱՆԱԿԱՆ**։ Յուրաքանչյուր նյութական փաստի կողքին տուր ուղղակի աղբյուրի հղում և ստուգման օր։

Առաջին պատասխանում պատրաստիր **իրագործելի որոշում և ճանապարհային քարտեզ**, այս հերթականությամբ.

1. Մեկ նախադասությամբ positioning և առաջին վճարող հաճախորդի ճշգրիտ նկարագիր. ինչ խնդրի համար կվճարի։
2. MVP-ի, երկրորդ փուլի և միջազգային փուլի պահանջներ՝ կոնկրետ ինչ էկրան/հոսք/հաշվարկ։ **Սկզբում մանրամասն արտահանման և ֆայլի ներմուծման ընթացքը**, հետո միայն API միացումները։
3. Ըստ աղբյուրի ֆայլային ներմուծման աղյուսակ՝ ինչ արտահանել, նվազագույն սյունակներ, նախընտրելի ֆորմատ, հաճախականություն, տվյալների որակ, պատասխանատու մարդ և fallback։ Դրանից հետո առանձին ավտոմատ ինտեգրացիաների աղյուսակ՝ պաշտոնական API, հաճախորդի թույլտվություն, գին/սահմանափակում, կախվածություն և իրական readiness. ՀԾ-Առևտուր 9, ՀԾ-Հաշվապահ 9, Meta, Instagram, TikTok, Telegram, հայկական բանկեր, Shopify, WooCommerce, Xero, QuickBooks։
4. Բանկերի համար հստակ եզրակացություն՝ **հաճախորդի ներբեռնած քաղվածքի ներմուծումը հիմա**, «ուղիղ API միայն պայմաններով» կամ այլ փաստերով հաստատված ուղի։ Առանձնացրու vPOS-ը հաշվի API-ից և բանկային մնացորդը շահույթից։ Տուր բանկերին հետագայում ուղարկվող հարցաշար։
5. Տեխնիկական ճարտարապետություն և նվազագույն data model/ERD, source of truth, sync և reconciliation flow, failure recovery, tenant isolation, security։
6. AI օգնականների tool boundaries, provenance, human approval, գնահատման 15–20 իմաստալից դեպքեր և չապացուցված causal claim-երի կանխարգելում։
7. Շաբաթ առ շաբաթ առաջին 30 օրը, ամիս առ ամիս մինչև 6 ամիս, և 12 ամսվա ընդլայնման քայլեր. յուրաքանչյուրի deliverable, owner/ունակություն, ծախսի միջակայք, կախվածություն և ընդունման պայման։
8. $1,000 կանխիկի կոնկրետ ծախսային պլան, մեկ հաճախորդի ամսական ինքնարժեքի երեք սցենար, գնի փորձարկում, առաջին երեք վճարող հաճախորդի ձեռքբերման ծրագիր։
9. Առաջին 10 տեխնիկական և բիզնես ռիսկերը՝ ազդեցություն, ստուգման փորձ և fallback։
10. Հստակ «սկսել վաղը» 10 գործողություն՝ առանց գոյություն չունեցող API-ներ սպասելու։

Գրիր հայերեն՝ միջազգային տերմինները փակագծերում անգլերենով։ Հիմնավորված որոշում կայացրու. մի ներկայացրու 5 հավասար լուծումներ առանց առաջնահերթության։ Հարցրու առավելագույնը երեք բացակայող տեղեկություն միայն վերջում, եթե դրանք կարող են փոխել ընտրված ուղղությունը։ Առաջին պատասխանից հետո առաջարկիր մեկ հաջորդ նեղ առաջադրանք՝ MVP-ի առաջին sprint-ի իրականացման համար։

Եթե հետագայում քեզ կտամ իրական repository կամ տվյալների օրինակներ, սկզբում կարդա առկա կոդը, API պայմանագրերը և տվյալների սխեման։ Մի փոխիր իրական հաճախորդի համակարգ, մի միացրու վճարում կամ գովազդ, և մի ընդունիր անհրաժեշտ credentials-ի գոյությունը, մինչև դրանք հստակ հասանելի և լիազորված չլինեն։
