# Варианты архитектуры

Критерии: $1 000 наличными, один разработчик с бэкграундом Java/QA/SQL и начальным TS, read-only интеграции, tenant isolation, объяснимость рекомендаций.

## Рекомендация: монолит «modular web app» (вариант A)

```
[Browser UI] ── HTTPS ── [API (TypeScript, Node) ]
                              │
                              ├── PostgreSQL (tenant_id + RLS)
                              ├── Import worker (очередь в той же БД: таблица jobs, SKIP LOCKED)
                              ├── Object storage для исходных файлов (локальный диск/S3-совместимый)
                              ├── Secrets: env + зашифрованная таблица credentials (для фазы API)
                              └── AI provider adapter (LLM по API; swap на локальную позже)
```

Почему:
- Один процесс, одна БД, один деплой. Очередь на PostgreSQL вместо Redis/RabbitMQ: достаточно для файлового импорта, минус ещё один сервис.
- RLS в PostgreSQL даёт проверяемую изоляцию tenant даже при ошибке в коде.
- Adapter для LLM изолирует провайдера; агенты получают только типизированные read-only функции.

Стек-гипотеза (ASSUMPTION, обсудить):
- Backend: TypeScript + Node (документ предлагает TS). **Альтернатива для основателя:** Java 25 + Spring Boot. Плюс: совпадает с его целью подтянуть Java до backend-уровня; сильная экосистема для XLSX (Apache POI), очередей, тестов (TestNG/Rest Assured уже знакомы). Минус: больше boilerplate, тяжелее хостинг по памяти. **Это решение надо принять осознанно**, см. [[Открытые вопросы к основателю]].
- UI: минимальный. Вариант 1: серверный рендер (Thymeleaf/HTMX при Java; EJS/HTMX при Node). Вариант 2: React + готовый admin-kit. Для одного человека HTMX дешевле на 50–100 часов (ASSUMPTION).
- БД: PostgreSQL 16+ с RLS. Миграции: Flyway/Liquibase (Java) или Prisma/Drizzle (TS).
- Хостинг: один VPS, Docker Compose, ежедневный pg_dump в объектное хранилище, **тест восстановления** раз в месяц.

## Альтернатива B: managed BI поверх PostgreSQL (Metabase / Apache Superset self-hosted)
- Плюс: ноль фронтенд-кода; дашборды за часы; SQL-основатель чувствует себя дома.
- Минус: multi-tenant в OSS-версиях ограничен (Metabase OSS — одна организация, разграничение через коллекции/sandboxing только в платной); армянская локализация частичная; AI-рекомендации с provenance придётся всё равно писать отдельно. (ASSUMPTION; лицензионные/функциональные детали UNVERIFIED в этой сессии.)
- Вердикт: хорош как **внутренний инструмент основателя** для пилотов, не как клиентский продукт.

## Альтернатива C: white-label (AgencyAnalytics и аналоги)
- Плюс: маркетинг-дашборд с коннекторами Meta/TikTok/Google за $20/клиент/мес (цена из документа на 2026-09-29, перепроверяется в [[Банки Армении]]).
- Минус: нет SKU/COGS/склада/банка; зависимость от условий вендора на экспорт и ресейл; данные клиентов у третьей стороны за рубежом (закон о ПД).
- Вердикт: не основа продукта. Возможно как **дополнение** для маркетолога клиента в фазе 3.

## Альтернатива D: enterprise custom (микросервисы, K8s, своя LLM)
- Отвергнуто. Нет команды, нет бюджета, нет нагрузки.

## Sync и reconciliation flow (файловая фаза)
1. Upload → сохранить файл + sha256 + uploader + tenant → `ImportBatch(status=uploaded)`.
2. Parse → `SourceRecord` построчно с `source_record_id` (из файла или детерминированный hash строки), `raw_payload jsonb`.
3. Map → применить сохранённый `ColumnMapping` для (tenant, source_system, file_signature); показать предпросмотр.
4. Validate → отчёт: дубли (по source_record_id внутри tenant), пропуски, валюта, SKU без alias, НДС-флаг не задан. Статусы `accepted / rejected / needs_review`.
5. Commit → upsert в доменные таблицы (SaleLine, ReturnLine, InventorySnapshot, CampaignDaily, BankTransaction) с `ingested_at`, `source_version`. Повторный файл с тем же hash → no-op с сообщением.
6. Reconcile → `ReconciliationMatch`: банк ↔ продажи (по дате/сумме/референсу), управленческие продажи ↔ бухгалтерский закрытый период. Расхождения не удаляются, а показываются с очередью объяснений.
7. Metrics → `MetricSnapshot` на период с версией формул (`formula_version`).
8. Recommend → `Recommendation` c inputs, formula_version, sources, freshness, confidence, llm_response_version; `Approval` человеком.

## Failure recovery
- Импорт транзакционен на уровне batch: либо commit, либо rollback с отчётом.
- Воркер идемпотентен: перезапуск job не создаёт дублей (ключ `tenant_id + source_system + source_record_id`).
- Исходный файл хранится до подтверждения + retention (например 90 дней), чтобы переиграть импорт после фикса парсера.

## Security baseline
- RLS по `tenant_id` + `SET LOCAL app.tenant_id` на каждую транзакцию.
- RBAC: owner, accountant, marketer, warehouse, admin; разные права на формулы и закрытие периода.
- Шифрование: TLS, диск/бэкапы зашифрованы; credentials (фаза API) — envelope encryption.
- AuditEvent на каждое изменение формул, mapping, approval, экспорт данных.
- Экран здоровья источников: last import, errors, covered period, (позже) permissions/credential expiry.

## Реализация (обновлено 2026-10-02)
Принято: Java 25 + Spring Boot 4.1.1 + PostgreSQL 16 + Flyway. Код в `app/`, описание в `app/README.md`.
Факты из первой итерации: в Boot 4 Flyway подключается через `spring-boot-starter-flyway` (не `flyway-core` напрямую), Jackson 3 живёт в пакете `tools.jackson`. В облачной песочнице нет Docker, поэтому интеграционные тесты идут на локальном PostgreSQL, не на Testcontainers.
