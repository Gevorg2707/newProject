# Глубокий анализ возможностей: что, как, почему

Легенда: **FACT** = подтверждено источником, **ASSUMPTION** = моя оценка, **UNVERIFIED** = не проверено, **CONDITIONAL** = технически возможно при условиях.

## 1. Что реально построить за $1 000 и в одиночку

**Вывод (ASSUMPTION, уверенность высокая):** файловый MVP технически реализуем одним человеком за 6–10 недель чистого времени и почти не требует денег. Деньги не являются узким местом. Узкое место — время основателя и доступ к реальным данным клиентов.

Почему:
- Файловый импорт CSV/XLSX, валидация, сверка и KPI — детерминированная логика без внешних зависимостей. Это сильная сторона основателя (SQL, тест-дизайн, API).
- Нет GPU, нет Kubernetes, нет лицензий. Хостинг на одном VPS. См. [[Варианты архитектуры]].
- LLM нужна только для объяснений на армянском и формулировки рекомендаций. Объём токенов в пилоте мал. Стоимость запроса надо замерить на реальных кейсах, не оценивать заранее (UNVERIFIED — конкретные цены провайдеров не проверялись в этой сессии).

Где уйдёт время (ASSUMPTION, по опыту аналогичных задач):

| Блок | Оценка часов | Комментарий |
|---|---|---|
| Импорт + mapping колонок + предпросмотр | 40–60 | XLSX парсинг, кодировки, армянские заголовки, даты, разделители |
| Идемпотентность, дедуп, качество данных | 30–40 | hash файла, source_record_id, отчёт ошибок |
| SKU matching / alias | 20–30 | один товар под разными кодами в POS, рекламе, складе |
| KPI-движок (net sales, GP, contribution, days of stock) | 30–40 | формулы фиксировать с бухгалтером **до** кода |
| Сверка банк ↔ продажи ↔ бухгалтерия | 30–50 | внутренние переводы, комиссии, частичные оплаты |
| Multi-tenant, RBAC, аудит | 30–40 | tenant_id везде, RLS в PostgreSQL |
| UI (6 экранов) | 60–100 | основатель новичок в React/TS → самый дорогой блок |
| LLM-слой рекомендаций + provenance | 20–30 | promt + schema + сохранение входов/версии |
| Тесты, деплой, бэкап/восстановление | 30–40 | |
| **Итого** | **290–430 ч** | 7–11 недель full-time или 4–6 мес. по вечерам |

**Рекомендация:** UI в MVP делать минимальным, серверно-рендеренным или на готовом admin-шаблоне, чтобы не платить временем за React-обучение в критическом пути. Альтернатива: первые 2 пилота вообще без UI — отчёт в Excel/PDF + разговор. Это сильнее проверяет готовность платить.

## 2. Почему файловый путь правильный (согласие с основателем)

- **FACT из документа:** ни один из источников не даёт подтверждённого права третьей стороне на API. Везде нужны ключи, пакеты, ревью приложения или договор. Проверка состояния на 2026-10-02: [[Сводная таблица интеграций]].
- **ASSUMPTION:** в малой рознице Армении данные уже живут в экспортах Excel для бухгалтера. Файл — путь наименьшего сопротивления и не требует разрешений ИТ-вендоров.
- Файловый путь даёт **честные данные о цене ручного труда**: сколько часов уходит на 1 клиента в месяц. Это основа для решения об автоматизации в фазе 2.

## 3. Что в документе требует критики

1. **Фаза 1 за 2–4 недели нереалистична** при полном scope (6 ролей, 2–3 рекомендации, сверка банка). Реально за 4 недели: импорт продаж + SKU + себестоимость + остатки, KPI и 1 тип рекомендации (пополнение). Банк и реклама — фаза 1b. (ASSUMPTION)
2. **Multi-tenant с первого дня — спорно.** 2 пилота можно обслужить отдельными схемами/БД. Но переделка позже дорогая. Компромисс: `tenant_id` в схеме с первого дня, RLS и self-service — позже. (ASSUMPTION)
3. **Цена 79–149 тыс. AMD/мес** при ручной работе 8–15 ч/мес на клиента даёт низкую маржу основателю. Надо замерить фактические часы на 2 пилотах до фиксации цены. (ASSUMPTION; рыночные цены UNVERIFIED)
4. **Четыре AI-ассистента в MVP избыточны.** Один «Analyst» с тремя режимами (finance/growth/inventory) на одном read-only tool-слое проще и безопаснее. Legal — не в MVP.
5. **ROAS и attribution**: документ правильно запрещает называть размеченные заказы «дополнительными продажами». Для малых бюджетов контролируемый эксперимент (geo/period split) часто статистически слаб. Честнее: показывать «до/после с оговорками» и доверительный интервал как «низкая уверенность». (ASSUMPTION)

| Прямой API банка для SaaS | **UNVERIFIED / скорее нет** | Ameriabank: 40 000 AMD/год, частный канал со своего IP, доков нет; другие банки молчат; Plaid Армению не покрывает |

## 5. Юридический контур (черновик, ждёт проверки закона)
- Персональные данные: в продажах розницы могут быть имена/телефоны покупателей. **Рекомендация:** не импортировать PII вообще в MVP — отсекать колонки на этапе mapping. Тогда большая часть закона о ПД не триггерится. Банковская выписка содержит контрагентов — хранить только агрегаты или псевдонимизировать. (ASSUMPTION до юриста)
- Трансграничная передача в LLM-провайдера: передавать только агрегаты и SKU-данные без PII. Юридическое заключение обязательно до реальных клиентов (требование документа).

## 6. Что я бы решил иначе (рекомендация первая, альтернативы одной строкой)

**Рекомендация:** «Консалтинг-first». Первые 2 платных пилота делаются Excel + SQL + ручной отчёт по шаблону, параллельно пишется импорт-ядро (backend без UI). UI появляется после 2-го платящего клиента.
- Альт. 1: сразу web-MVP с UI. Плюс: демо для продаж. Минус: 100+ часов на фронт до первой оплаты.
- Альт. 2: managed BI (Metabase/Superset self-hosted) поверх PostgreSQL как UI. Плюс: ноль фронт-кода. Минус: мультитенантность и армянская локализация ограничены; разбор отдельно в [[Варианты архитектуры]].
- Альт. 3: white-label (AgencyAnalytics). Плюс: быстрый маркетинг-дашборд. Минус: не покрывает SKU/финансы, зависимость от условий вендора. См. [[Банки Армении]] раздел про AgencyAnalytics после проверки.
